#### 1. 项目背景：为什么学习机器人需要"记忆"

现有的 AI 学习助手（包括通用大模型对话）有一个共同的结构性缺陷：**每次对话结束，一切清零。**

- 用户练了三个月英语，系统对用户的了解和第一天一样
- 机器人不知道用户上次犯了什么错、这周在忙什么、学习目标是什么
- 每次交互都是独立事件，无法形成持续的教学关系

小伴 要解决的核心问题：**让学习机器人真正"认识"用户，实现跨会话的个性化教学。**

这不只是一个技术 Feature——它改变了人机交互的本质：从"使用工具"变成"和私教相处"。

##### 2.2 与文心大模型的交互方式

文心大模型在 Agent 链路中承担 **3 个角色**，每个角色对应一次 API 调用：

| 角色 | 调用点 | 输入 | 输出 | 模型 | temperature |
|------|--------|------|------|------|------------|
| 意图分类器 | 调用 1 | 用户文本 + 上下文 | intent JSON | ERNIE-4.0-Turbo | 0.1 |
| 教学规划器 | 调用 2 | 意图 + 画像 + FSRS 卡片 | 教学步骤 JSON | ERNIE-4.0-Turbo | 0.3 |
| 对话教练 | 调用 3 | 教学计划 + 记忆 + 历史 | 自然语言回复 | ERNIE-4.0-8K | 0.7 |

**为什么拆成 3 次调用而不是 1 次？**

- **可观测性**：每一步的输入输出都可审查，便于调试和优化
- **可控性**：意图识别用低 temperature 保证准确，对话生成用高 temperature 保证自然
- **可替换性**：任意一层可以独立升级模型或替换为规则引擎

#### 3. 关键实现步骤

##### 3.1 文心大模型 API 接入（千帆 v2 协议）

通过千帆 v2 API 调用（OpenAI 兼容格式 + IAM 安全认证），核心代码结构：

```python
# app/services/ernie_client.py

BASE_URL = "https://qianfan.baidubce.com/v2"

def _get_headers() -> dict:
    """IAM 认证 Header"""
    return {
        "Authorization": f"Bearer {settings.BAIDU_API_KEY}",
        "Content-Type": "application/json",
    }

async def chat(messages, model="ernie-4.0-turbo-8k", temperature=0.7, max_tokens=1024):
    """
    调用文心大模型 v2 API（OpenAI 兼容格式）

    Args:
        messages: [{"role": "system"|"user"|"assistant", "content": "..."}]
                  v2 协议原生支持 system role
        model: 模型标识
        temperature: 0.0-1.0

    Returns:
        {"content": "模型回复", "usage": {"total_tokens": N}}
    """
    body = {"model": model, "messages": messages,
            "temperature": temperature, "max_tokens": max_tokens}
    async with httpx.AsyncClient(timeout=30.0) as client:
        resp = await client.post(
            f"{BASE_URL}/chat/completions", headers=_get_headers(), json=body)
        data = resp.json()
    return {"content": data["choices"][0]["message"]["content"],
            "usage": data.get("usage", {})}
```

**关键参数说明**：

| 参数 | 值 | 说明 |
|------|---|------|
| Authorization | Bearer {IAM Key} | 千帆 v2 IAM 安全认证，不再使用 access_token |
| model | ernie-4.0-turbo-8k | 支持 8K 上下文，请求体中指定 |
| temperature | 0.1 / 0.3 / 0.7 | 按调用点分别设置 |
| response_format | {"type": "json_object"} | 调用 1/2 使用，强制 JSON 输出 |

##### 3.3 FSRS 记忆调度引擎

```python
# app/services/fsrs_utils.py — 已有实现

from fsrs import FSRS, Card, Rating

scheduler = FSRS()

def schedule_review(card: Card, rating: Rating) -> Card:
    """
    根据用户表现更新卡片的复习参数

    Rating:
      Again  — 完全忘记，1 分钟后再复习
      Hard   — 勉强记得，间隔缩短
      Good   — 正常记得，正常间隔
      Easy   — 轻松记得，大幅延长间隔

    Returns:
        更新后的 Card（含下次复习时间 due）
    """
    scheduling_cards = scheduler.repeat(card, datetime.now(timezone.utc))
    updated = scheduling_cards[rating].card
    # updated.due = 下次应复习时间
    # updated.stability = 记忆稳定性
    # updated.difficulty = 知识点难度
    return updated

def get_due_cards(user_id: str) -> list:
    """获取当前到期需要复习的卡片列表"""
    now = datetime.now(timezone.utc)
    return db.query(GrammarCard).filter(
        GrammarCard.user_id == user_id,
        GrammarCard.due <= now
    ).order_by(GrammarCard.difficulty.desc()).all()
```

##### 3.5 容错处理机制

```python
# app/services/ernie_client.py

ERNIE_MODELS = [
    "ernie-4.0-turbo-8k",   # 首选：高质量
    "ernie-3.5-turbo-128k",  # 降级：更低延迟、更高可用性
]

async def chat_with_retry(messages, temperature=0.7, max_tokens=1024, **kwargs):
    """
    带重试和模型降级的文心 API 调用（v2 协议）

    策略：ERNIE-4.0 超时 → 重试 1 次 → 降级到 ERNIE-3.5
    全链路基于百度文心生态，IAM 认证。
    """
    for model in ERNIE_MODELS:
        for attempt in range(2):
            try:
                result = await asyncio.wait_for(
                    chat(messages, model=model, temperature=temperature,
                         max_tokens=max_tokens, **kwargs),
                    timeout=15.0,
                )
                if model != ERNIE_MODELS[0]:
                    logger.warning("已降级到 %s", model)
                return result
            except (asyncio.TimeoutError, httpx.HTTPError, RuntimeError) as e:
                logger.warning("%s 第 %d 次调用失败: %s", model, attempt + 1, e)
                if attempt == 0:
                    await asyncio.sleep(1)
                continue
        continue

    return {"content": "抱歉，AI 服务暂时不可用。你可以查看学习卡片进行手动复习。", "usage": {}}
```

#### 4. 核心创新：不只是聊天机器人——小伴 的四层能力

小伴 与普通 AI 聊天机器人的区别不在于某个单点技术，而在于**四层能力的协同**：

##### 4.1 能力一：Agent 架构——理解复杂指令

普通聊天机器人只做一件事：收到文本 → 调用 LLM → 返回回复。小伴 的 Agent 架构将一次交互拆解为 3 步：

```
普通聊天机器人：  用户说话 → LLM → 回复（一步到位，不可控）

小伴 Agent： 用户说话 → 意图理解 → 任务规划 → 对话生成（分步可控）
                              ↑           ↑           ↑
                          文心调用1    文心调用2    文心调用3
                         （这是什么）  （该做什么）  （怎么说）
```

这意味着机器人能处理复合指令："帮我复习上次的错误，但跳过我已经掌握的"——需要先理解意图，再查询记忆筛选卡片，最后生成对话。

##### 4.2 能力二：长期记忆——跨会话认识用户

```
┌─ user_profile ──────────────────┐
│  用户是谁：职业、英语水平、学习目标 │
│  更新频率：每 10 次对话             │
│  作用：决定话题方向和难度           │
└─────────────────────────────────┘

┌─ user_facts ────────────────────┐
│  用户近况：本周发生了什么            │
│  更新频率：每次对话后提取 2-3 条     │
│  作用：让对话贴合用户真实生活        │
│  示例："用户下周有英文演讲"          │
└─────────────────────────────────┘

┌─ grammar_cards ─────────────────┐
│  知识卡片：用户反复出错的知识点      │
│  调度算法：FSRS 6                  │
│  作用：精确控制每个知识点的复习时机   │
│  示例：go/went 过去时，下次复习 5/10 │
└─────────────────────────────────┘
```

三层记忆协同工作：profile 决定"教什么方向"，facts 决定"用什么话题"，cards 决定"强化哪个知识点"。每次对话后异步更新，用户无需手动管理。

##### 4.3 能力三：科学调度——FSRS 算法驱动教学节奏

FSRS（Free Spaced Repetition Scheduler）基于记忆科学的间隔重复算法，核心逻辑：**在用户即将遗忘的时刻复习，记忆效率最高。**

```
Day 1: 用户说 "I go to meeting yesterday"
  → 系统创建卡片：go/went 过去时
  → FSRS 计算：1 天后复习

Day 2: FSRS 标记卡片到期
  → Agent 规划器将 go/went 纳入今天的教学计划
  → 对话中，机器人自然说 "How did your meeting go yesterday?"
  → 用户正确使用 went → FSRS 更新间隔为 3 天
  → 用户仍说 go → FSRS 缩短间隔为 1 天

Day 5 → Day 12 → Day 30 → ...
  → 间隔逐渐拉长，直到用户彻底掌握
```

**FSRS 不是 小伴 的全部，但它是"自主教学"的关键——让机器人从"你问我答"变成"我知道今天该教你什么"。**

##### 4.4 能力四：具身交互——硬件让陪伴变得真实

这是 小伴 最终要解决的问题：**软件再智能，用户关掉 App 它就不存在了。**

RDK X3 硬件赋予机器人三个纯软件做不到的能力：

| 硬件能力 | 实现方式 | 教学价值 |
|---------|---------|---------|
| **看到用户** | 摄像头 + BPU 表情识别 | 检测困惑/走神/疲惫，自适应调整教学节奏 |
| **物理反馈** | 舵机（点头/摇头）+ LED | 多感官正反馈，强化学习效果（教育心理学实证） |
| **主动发起** | 检测用户坐下/接近 | 不等用户打开 App，主动说"今天有 3 个知识点到期" |
| **端侧推理** | BPU 运行 STT/TTS | 语音不上云（隐私），响应更快（低延迟） |

阶段 1 验证前三层能力（Agent + 记忆 + 调度），阶段 2 加上第四层（具身交互）——灵魂先跑通，再装进身体。

#### 6. 失败场景处理

| # | 异常场景 | 检测方式 | 处理策略 | 用户感知 |
|---|---------|---------|---------|---------|
| 1 | STT 识别失败 | 转录结果为空或置信度 <0.3 | 提示重试 + 显示文本输入框 | "没听清，请再说一次，或者打字告诉我" |
| 2 | 文心 API 超时 | asyncio.wait_for 8s | 重试 1 次 → 降级到 ERNIE-3.5-Turbo | 用户无感，日志记录 |
| 3 | 千帆平台不可用 | ERNIE-4.0 和 3.5 均失败 | 纯本地模式：展示 FSRS 卡片 | "AI 暂时离线，先看看今天的复习卡片" |
| 4 | 意图识别失信 | confidence < 0.5 | 进入自由聊天模式 | 机器人正常聊天，不执行错误操作 |
| 5 | 异常输入 | 空文本/超长文本/注入攻击 | 输入校验 + 截断 + 过滤 | "请说一句完整的话，我来帮你" |

#### 7. 阶段 2 硬件方案：RDK X3 部署架构

阶段 1 验证 Agent 大脑（灵魂），阶段 2 将大脑装进 RDK X3 实体机器人（身体）。

##### 7.1 阶段对照

| 组件 | 阶段 1（软件验证） | 阶段 2（RDK X3 实体） | 硬件带来的增益 |
|------|-------------------|---------------------|-------------|
| STT | 百度短语音识别（极速版） | 端侧 hobot_asr（BPU） | 延迟进一步降低，语音不出设备 |
| TTS | 百度语音合成（在线） | 端侧 hobot_tts | 断网可用，响应更快 |
| 视觉 | 无 | MIPI 摄像头 + BPU 推理 | 表情感知、教材识别、主动交互 |
| 物理交互 | 屏幕 UI | 舵机 + LED | 点头/摇头反馈、状态灯指示 |
| LLM | 云端文心 API | 云端文心 API | 决策层仍走云端（5 TOPS 不足以跑 LLM） |
| 中间件 | FastAPI HTTP | ROS 2 Topic（TogetheROS.Bot） | 标准机器人通信框架 |

##### 7.2 RDK X3 硬件规格与能力适配

| 硬件 | 规格 | 对 小伴 的作用 |
|------|------|-------------------|
| CPU | 4 核 Cortex-A53 @ 1.5GHz | 运行 Agent 服务、ROS 2 节点 |
| BPU | 5 TOPS（Bernoulli 架构） | 端侧 STT/TTS/表情识别推理 |
| 摄像头 | 2× MIPI CSI | 用户表情捕捉、教材内容识别 |
| GPIO | 40-pin（兼容树莓派） | 驱动舵机（PWM）、LED（GPIO） |
| 音频 | USB 麦克风 + 3.5mm 扬声器 | 语音输入输出 |
| 网络 | Wi-Fi 5GHz + 千兆以太网 | 文心 API 云端调用 |

#### 8. 为什么需要实体机器人——硬件带来的不可替代价值

一个关键问题：既然阶段 1 是纯软件 Demo，为什么最终目标是部署到 RDK X3 实体硬件？

**因为"陪伴式学习"这件事，软件只能解决一半。**

| 维度 | 纯软件（App/网页） | 实体机器人（RDK X3） |
|------|-------------------|---------------------|
| 存在感 | 打开 App 才存在，关掉就消失 | 放在书桌上，物理存在，随时可交互 |
| 情感连接 | 屏幕上的文字/语音 | 点头鼓励、摇头提醒、LED 呼吸灯表示"在听" |
| 感知能力 | 只有麦克风（语音） | 麦克风 + 摄像头（看到用户表情、识别教材内容） |
| 主动性 | 用户不打开就沉默 | 检测到用户坐下，主动说"今天有 3 个知识点到期了" |
| 隐私 | 数据上云 | 端侧 BPU 推理，语音/视觉数据不出设备 |
| 延迟 | 依赖网络 | STT/TTS 端侧运行（hobot_asr/hobot_tts），响应更快 |

具体来说，RDK X3 硬件解锁了 3 个纯软件做不到的能力：

**能力 1：具身感知——看到用户的状态**

摄像头 + BPU（5 TOPS）实时推理用户表情：
- 检测到用户皱眉/困惑 → 自动放慢节奏、给出更多解释
- 检测到用户走神/分心 → 切换话题或发起互动
- 识别用户手持教材 → 自动进入"教材辅导"模式

这让机器人从"被动回答"变成"主动感知"——不需要用户说"我不懂"，它能看出来。

**能力 2：具身反馈——物理动作强化学习效果**

教育心理学研究表明，多感官反馈比纯文字/语音更能加深记忆：
- 用户说对了 → 机器人点头 + LED 变绿 + 语音鼓励（三重正反馈）
- 用户说错了 → 机器人轻摇头 + LED 变黄 + 语音温和纠正
- 复习完成 → 机器人"举手"庆祝

这不是花哨——**物理反馈让"学习效果"变得可感知**，尤其对儿童/青少年用户。

**能力 3：端侧推理——隐私与低延迟**

RDK X3 的 BPU 支持端侧 STT/TTS 推理（hobot_asr + hobot_tts）：
- 用户语音不上传云端，BPU 本地处理
- STT 延迟从云端进一步降低到端侧 ~100ms
- 断网仍可进行基本的语音交互（不依赖百度云端服务）

**阶段 1 与阶段 2 的关系**：阶段 1 的 Agent 大脑（文心 API + 记忆系统 + FSRS 调度）是"灵魂"，阶段 2 的 RDK X3 硬件是"身体"。灵魂先验证跑通，再装进身体——这是机器人开发的正确路径。

---

#### 9. 总结

小伴 的核心命题是：**一个学习机器人如果不认识用户，就只是一个带语音的搜索引擎。**

我们通过三层能力构建了一个真正"认识用户"的学习机器人：

1. **Agent 架构（文心大模型 × 3 次调用）**——让机器人能理解意图、规划教学、生成个性化对话，而不是简单的一问一答
2. **长期记忆系统（用户画像 + 生活事实 + 知识卡片）**——让机器人跨会话积累对用户的认知，每次交互都比上次更精准
3. **科学调度引擎（FSRS 算法）**——让机器人基于记忆科学自主决定教什么、什么时候教，而不是随机或固定课程
4. **具身交互（RDK X3 硬件）**——让机器人从屏幕走向桌面，通过视觉感知用户状态、通过物理动作强化学习反馈、通过端侧推理保障隐私与低延迟

这四层能力缺一不可：没有 Agent 架构就无法理解复杂指令，没有记忆就不认识用户，没有调度就是随机教学，没有硬件就只是一个 App。
