# 飞桨黑客松第10期 · 进阶任务 #13 项目方案

**项目名称**：基于 PaddleOCR-VL + OpenVINO 的产品文档智能入库与客服问答系统

**一句话描述**：让任意格式的产品手册在 5 分钟内变成可问答的知识库。

---

## 一、应用场景

**目标用户**：拥有大量产品手册 / 技术文档的企业客服团队。

**核心痛点**：

1. 企业产品文档格式复杂（扫描件 PDF、图文混排、含表格 / 公式的规格书），传统 OCR + RAG 方案难以正确解析。
2. 人工整理文档入库成本高、周期长，知识库"冷启动"困难。
3. 客服人员需反复翻阅手册回答重复性问题，响应慢、易出错。

**典型场景**：

- 某硬件厂商有 200+ 份产品规格书（PDF 扫描件），需要快速建立客服知识库。
- 客户询问"XX 型号的工作温度范围是多少？"——答案藏在某份规格书表格的第 3 行。

---

## 二、与现有 OpenVINO Notebooks 的差异

经排查，现有 OpenVINO Notebooks 仓库中存在两类相关工作：

- **PaddleOCR-VL Notebook**：单模型推理演示（图片 → 识别结果），无 RAG 链路。
- **RAG Notebook**（LangChain + OpenVINO）：使用 Unstructured + Tesseract 解析文档，只能处理机器可读 PDF。

**本方案的组合创新**：将 PaddleOCR-VL 的文档理解能力嵌入 RAG 链路，填补"复杂文档 → 可问答知识库"这一环节的空白。

| 维度 | 现有 RAG Notebook | 本方案 |
|------|-------------------|--------|
| 文档解析 | Unstructured + Tesseract | **PaddleOCR-VL**（OpenVINO 加速） |
| 可处理文档 | 机器可读 PDF、纯文本 | 扫描件、图文混排、含表格 / 公式的手册 |
| 表格处理 | 提取为 HTML，能力有限 | 原生理解表格结构，保留行列语义 |
| 切片策略 | 固定长度切片 | 表格行 + 表头为 chunk，段落按语义切 |
| 端到端场景 | 通用问答 | **产品文档零人工入库 → 客服问答** 完整链路 |

---

## 三、技术思路

采用 **上游入库 + 下游问答** 两段式架构，纯 Python 实现，全链路代码透明。

### 上游：文档智能解析与入库

```
原始产品文档（PDF / 扫描件 / 图片）
        ↓
   PaddleOCR-VL（OpenVINO 加速）
   → 识别文字、表格、公式、图表
   → 输出结构化 Markdown
        ↓
   智能切片（表格感知 + 语义段落）
        ↓
   Embedding 向量化 → 存入向量数据库
```

**关键设计**：

1. **表格感知切片**
   - 表格内容：每行数据 + 表头组成一个 chunk，保证检索到任意一行都能还原完整语义。
   - 非表格内容：按语义段落切分，chunk 大小 300–500 字符。
   - 每个 chunk 携带元数据（来源文档名、页码、章节标题），支持答案溯源。

2. **多格式适配**
   - PDF 先判断是否为机器可读（尝试直接提取文字），不可读时走 PaddleOCR-VL 路径。

### 下游：检索增强问答

```
用户提问
    ↓
Query Embedding → 向量检索 Top-K 相关片段
    ↓
Prompt 拼装（系统指令 + 检索片段 + 用户问题）
    ↓
LLM 生成回答（OpenVINO 加速推理）
    ↓
返回答案 + 来源引用（文档名 + 页码）
```

## 四、工具与框架

| 组件 | 选型 | 说明 |
|------|------|------|
| 文档解析 | **PaddleOCR-VL**（0.9B） | 核心差异化组件，109 种语言，表格 / 公式 / 图表原生理解 |
| 推理加速 | **OpenVINO** | 对 PaddleOCR-VL、Embedding、LLM 三个模型统一加速 |
| 向量数据库 | **ChromaDB** | 轻量级，Notebook 内直接运行，无外部服务依赖 |
| Embedding | **BGE-small**（OpenVINO 加速） | 轻量高效，支持中英文 |
| LLM | **Qwen3-1.7B**（OpenVINO INT4，HF `OpenVINO/Qwen3-1.7B-int4-ov` 现成 IR） | 本地 CPU 运行，无需 API；RAG 场景关 thinking 模式 |
| 编排 | **纯 Python** | 全链路代码透明，每一步可审查 |
| 前端展示 | **Gradio**（可选） | 时间充裕则加入交互界面 |

## 五、预期效果

### 功能效果

1. **5 分钟入库**：上传任意格式产品手册，自动完成 解析 → 切片 → 向量化 全流程。
2. **精准表格问答**：能正确回答"XX 型号参数是多少"这类需要定位表格单元格的问题。
3. **来源可溯**：每个回答附带引用来源（文档名 + 页码），支持人工核验。

### 性能指标（预期 → 实测）

| 指标 | 预期 | 实测 (2026-05-12, Intel AI PC, OV 2026.1) |
|------|------|--------------------------------------------|
| PaddleOCR-VL 推理（10 张混合测试图均值） | OV vs PT 加速比 ≥ 2x | **OV CPU 2948 ms / OV GPU 2003 ms**（GPU/CPU 加速 1.47x）<br>PT FP32 CPU 单图实测 ≈ 360 s（intractable，详见脚注 1） |
| LLM 首 token 延迟（INT4 量化，Intel CPU） | < 2s | Phase 3 后填 |
| 端到端问答响应（CPU） | < 15s | Phase 3 后填 |
| 扫描件文字识别 — 14 页中文 GB 标准 | 端到端跑通 + 切出含表结构 | **87 chunks（1 表头 + 6 表行 + 80 文本）/ 14 OCR 页**；OCR 时长 ≈ 22 s/页（CPU）（详见脚注 2） |

> 完整数据见 `openvino/results/phase1/benchmark_inference.cpu.md` / `openvino/results/phase1/gpu/benchmark_inference.md` / `openvino/results/phase2/gb_t_2423_1.summary.json`。

**脚注**：

1. **为何 PT 基线被弃测**：PaddleOCR-VL HF 远端代码默认 FP32，本机 torch 2.11.0+cpu 上 1 张 text_01 (32 max_new_tokens) 实测 ≈ 360 s；按 2048 默认 token、10 张 × 3 次 估算需 ~15 hr，单机不可行。同时 OpenVINO IR 自带 INT4 + INT8 量化，"OV vs PT" 实质混合了"框架 + 量化"两个变量，单独的 OV-vs-PT 加速比解释力有限。改用"OV CPU vs OV GPU"做框架内部对照，更贴近 Intel AI PC 部署场景。NPU 数据本周补。
2. **扫描件路径证据**：W1 测试用合成图只产出 1 chunk，是工程占位；本次 W2 用 GB/T 2423.1-2008 真实扫描件，14 页全走 PaddleOCR-VL OCR 路径，切出 87 chunks 且 7 行表格被正确识别带表头进入向量库（满足 §三 表格感知切片设计要求）。识别准确率的客观量化由 §七 OmniDocBench 子集承担，不依赖单一文档自评。

### Demo 规划

**核心演示：Tesseract vs PaddleOCR-VL 对比**（置于 Notebook 最前，先建立说服力）

1. 选取一份表格密集的扫描件产品规格书。
2. 分别用 Tesseract 和 PaddleOCR-VL 解析，并排展示解析结果。
3. 用同一个问题（如"XX 型号的额定功率是多少？"）分别在两个解析结果建的知识库上检索。
4. 对比回答质量：Tesseract 方案答错 / 答不出 vs PaddleOCR-VL 方案精准命中。

**完整流程演示**：准备 3–5 份真实产品手册（纯文本 PDF、扫描件、含表格规格书），展示从上传到可问答的端到端流程。

## 七、评测体系

不止 cherry-pick 几份文档做演示。Phase 4 评测分三层证据，保证结论可复现、可量化。

### 7.1 三层证据架构

```
   ┌─────────────────────────────────────────────────────────────┐
   │ ① 客观对照  ──  OmniDocBench 子集 (CVPR 2025 公认基准)      │
   │    20 页样本 × {Tesseract, PaddleOCR-VL}                    │
   │    指标：Edit Distance（文本）/ TEDS（表格）/ CDM（公式）   │
   │    → 证明 PaddleOCR-VL 在公开基准上优于 Tesseract           │
   └─────────────────────────────────────────────────────────────┘
   ┌─────────────────────────────────────────────────────────────┐
   │ ② 业务场景  ──  自建 30~50 题 / 5 份公开 PDF                │
   │    类型分布: 单表查询 35% / 概念 25% / 跨文档 20% /         │
   │              拒答 15% / 公式 5% (参考 MMLongBench-Doc)      │
   │    → 证明在"产品手册客服问答"场景下端到端可用              │
   └─────────────────────────────────────────────────────────────┘
   ┌─────────────────────────────────────────────────────────────┐
   │ ③ 自动评测  ──  RAGAS                                       │
   │    指标：faithfulness / answer_relevancy /                  │
   │           context_precision / context_recall                │
   │    → 用同一套数据反映检索 + 生成两段的质量                  │
   └─────────────────────────────────────────────────────────────┘
```

### 7.2 评测材料

| 用途 | 来源 | 数量 | 获取方式 |
|------|------|------|---------|
| 客观对照（OmniDocBench 子集）| HF `opendatalab/OmniDocBench` | 20 页 | `scripts/download_eval_materials.py --omnidoc-samples 20` |
| 业务 demo（PaddleOCR-VL 论文） | arXiv 2510.14528 / 2601.21957 | 2 份 | 自动下载 |
| 业务 demo（NVIDIA H100 系列） | NVIDIA Product Briefs | 2 份 | 自动下载（PB-11133-001 / PB-11773-001）|
| 业务 demo（中文规格 / 客服） | 昆仑芯 / 小米 / GB/T | 3 份 | 人工下载（站点限制）|
| 业务评测集 | 自建 `eval_questions.jsonl` | 18+ 题 | 仓库跟踪 |

**为什么不全自建**：评委是 Intel + 百度 OpenVINO 团队，看 cherry-pick 出来的样本会怀疑结论可信度。挂一个 CVPR 2025 公认基准的子集，把"我们的方法在公开数据上也成立"作为底牌。

**为什么不用 OmniDocBench 全集**：6 GB 数据 + 几小时推理，对 5 周开发周期太重；20 页足以做差异显著性检验，预算合理。

### 7.3 评测指标对接

| 评测项 | 实现 | 工具 |
|--------|------|------|
| Edit Distance / TEDS / CDM | 调 OmniDocBench 官方 `pdf_validation/` 脚本 | <https://github.com/opendatalab/OmniDocBench> |
| `keyword_match` 题 | 自动脚本，外层 AND / 内层 OR 逻辑 | 本仓库 |
| `must_refuse` 题 | 检测拒答关键词 + 无"编造细节" | 本仓库 |
| `manual_rubric` 题 | 人工 0 / 0.5 / 1 三档 | 人工 |
| 端到端 RAG | faithfulness 等 4 指标 | [RAGAS](https://docs.ragas.io) |
